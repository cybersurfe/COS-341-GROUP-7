# SPL Parser (COS341 2026, Semester Practical, Phase 1)

A lexer and recursive-descent parser for the Students' Programming Language (SPL). It reads an SPL source file, checks it against the SPL grammar, and writes the syntax tree to `tree.xml`. If the program is invalid, it prints a syntax or lexical error with the line and column, plus a hint.

## Build and run

```bash
javac Lexer.java Parser.java

# parse SPL.txt (default) and write tree.xml
java Parser

# parse a specific file
java Parser path/to/program.txt
```

## Architecture

We use a **separate lexer plugged in front of the parser**, not a lexer-less parser.

- Every SPL token ends with a blank, so the lexer only needs to split on blanks and classify each chunk.
- The parser works on tokens, so lookahead is cheap.
- Lexical errors (bad number or name) and syntax errors (wrong token order) come from different places, which makes the messages easier to tailor.

### Lexer

- Blank characters: space, LF, CR (CRLF counts as one line break) and tab.
- Each blank-separated chunk is classified in this order: keyword, symbol, name, string, number. Anything else raises a `LexException` with a hint. For example, `(#x)` gives "every token must be followed by a blank space".
- NUM, USER-DEFINED-NAME and STRING follow the regular expressions in the spec. That includes no leading zeros, no trailing zero in the fraction, and `-0` rejected.
- The en dash (`–`) is accepted and normalised to `-`.
- A UTF-8 BOM at the start of the file is stripped.
- The `$` end-of-input token is generated by the lexer and does not appear in `SPL.txt`.

### Parser

A recursive-descent parser (Mogensen, *Introduction to Compiler Design*, section 2.11.1). Each non-terminal is one function. Each function returns a finished subtree, and the caller attaches it to its own node.

## Is the grammar LL(1)?

Almost, but not strictly.

**Nullable non-terminals:** V_DECL, F_DECL, ALGO, INPUT. Each has exactly one epsilon production. For each one, FIRST and FOLLOW do not overlap:

| Non-terminal | FIRST | FOLLOW |
|--------------|-------|--------|
| V_DECL | `NAME` | `:` `)` |
| F_DECL | `void` `num` | `:` |
| ALGO | `NAME` `print` `nop` `comment` `if` `while` `until` `do` | `$` `return` `}` |
| INPUT | `NAME` `NUM` `mod` `add` `sub` `mul` `div` `neg` | `)` |

**Two FIRST/FIRST conflicts**, both on `NAME`:

1. `INSTR -> ASSIGN | CALL` (`NAME = TERM` vs `NAME ( INPUT )`)
2. `TERM -> NAME | CALL` (`NAME` vs `NAME ( INPUT )`)

We did **not** left-factor the grammar, because the spec wants real `ASSIGN` and `CALL` nodes in `tree.xml` and later phases depend on them. Instead, the parser peeks one extra token: after a `NAME`, `=` means ASSIGN and `(` means CALL. In TERM, `(` means CALL and anything else means a plain variable. This is safe because nothing in the grammar allows `(` directly after a TERM. The parser is therefore LL(2) at exactly those two spots and LL(1) everywhere else.

There is no left recursion, so no rewriting was needed. The grammar's rule `SPL_PROG -> P $` corresponds to `parseProgram()`.

## Output: `tree.xml`

One `<node id="...">` per tree node, in pre-order. IDs come from a single counter, so they are unique and increase through the file.

| Node type | Fields |
|-----------|--------|
| Root (`SPL_PROG`) | `contents`, `children` |
| Inner node | `contents`, `children`, `parent` |
| Leaf (terminal token) | `contents`, `parent` |

`children` is a comma-separated list of IDs.

Example shape:

```xml
<tree>
  <node id="1">
    <contents>SPL_PROG</contents>
    <children>2</children>
  </node>
  <node id="2">
    <contents>P</contents>
    <children>3,4,5,6,7</children>
    <parent>1</parent>
  </node>
  ...
  <node id="9">
    <contents>#x</contents>
    <parent>3</parent>
  </node>
</tree>
```

Design decisions:

- **Epsilon productions** produce an inner node with an empty `<children></children>`. For example, an empty V_DECL still appears in the tree.
- **`$` is not a leaf.** It is only a meta symbol for the parser and is not part of the input file. It is still checked, and any trailing tokens are reported as an error.
- **Terminal text** is written exactly as the lexer produced it, with `-` in place of the en dash. Special XML characters are escaped.
- The tree is built in memory and written in one go, so a failure never leaves a half-written file.

## Error messages

- **Lexical:** `Lexical error at line L, column C: Invalid token '...'. <hint>`
- **Syntax:** `Syntax error at line L, column C: expected '...' but found '...' (KIND).`

Hints cover common mistakes: missing `#` on a name, uppercase keywords, `+` signs, leading zeros, a missing space before or after a symbol, and strings containing spaces or uppercase letters.

## Known limitations and choices

- **Trailing blank on the last token:** the spec says every token ends with a blank. We accept a file whose last token has no trailing blank (`STRICT_EOF_BLANK = false` in `Lexer.java`). Set it to `true` for a strict reading.
- **Tab is accepted as a blank,** although the spec lists only ASCII 32 and 13. LF is accepted as well, for Linux-style line endings.
- **Lexical errors are reported first.** The whole file is tokenised before parsing, so a lexical error late in the file hides an earlier syntax error.
- **Semantic rules are not checked here.** Scope analysis, type checking, "call as instruction must be void", and the `mod`/`div` restrictions belong to later phases. The parser only checks structure.
- **Stale output:** if a run fails, a `tree.xml` from an earlier run is not deleted. Do not mistake it for output of the failing input.
